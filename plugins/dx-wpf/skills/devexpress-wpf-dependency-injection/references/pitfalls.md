# Pitfalls

Each entry: symptom → cause → what to do.

## Provider configured too late
`InvalidOperationException` from `IocExtension` at startup ("IocServiceProvider is not configured") → XAML that uses `{dxmvvm:Ioc}` loaded before `ConfigureServices` ran: `StartupUri`, `App.xaml` resources, or a window created before the call. → Configure first; see `wiring.md` → Composition root.

## Unregistered type resolves to null
The window opens empty, bindings silently show nothing → `{dxmvvm:Ioc Type=X}` asks the provider for exactly `X`; if `X` is not registered (or only its interface is), the result is `null` and no exception is thrown. → Register the exact type used in XAML; `ValidateOnBuild` does not catch this because XAML lookups are not known to the container.

## POCO view models
Commands and property notifications stop working after migration → a runtime-generated POCO view model (`ViewModelSource.Create`, `dxmvvm:ViewModelSource`) was replaced by a plain registration of its class, so the container creates the non-generated type. DevExpress locators also skip runtime-generated POCO types. → Register the generated type under the view model type (`ViewModelSource.GetPOCOType(typeof(X))`, see `wiring.md` → "Verified API facts") and keep resolving `X` — or register a factory that creates it through `ViewModelSource.Create(() => new X(...))`. Converting to compile-time `[GenerateViewModel]` view models also works, but is a style change — only with the user's consent, otherwise report it as an option.

## Dependency is `null` in an override the base constructor calls
`NullReferenceException` at startup, in an override such as `CreateModules()` → the base class constructor calls a virtual method (DevExpress `DocumentsViewModel` calls `CreateModules()`), and C# runs it before the derived constructor body, so a field assigned there is still `null`:
```csharp
public MainViewModel(IUnitOfWorkFactory<IMyUnitOfWork> factory) : base(factory) {
    this.factory = factory;                  // runs after base(...) already called CreateModules()
}
protected override Module[] CreateModules() => BuildModules(factory);   // factory is null here
```
→ In such an override, use what the base class already holds (`DocumentsViewModel` keeps the factory in its protected `unitOfWorkFactory` field) or create the value lazily on first use — never a field of the derived class. Look for this whenever a view model passes a constructor parameter to `base(...)` and overrides a method.

## Scaffolded view model with a protected constructor
`InvalidOperationException` "A suitable constructor for type 'X' could not be located" when the view opens → view models generated by the DevExpress Scaffolding Wizard (and the DevExpress demos) are POCO classes with only a `protected` constructor and a static `Create(...)` that builds the generated type; `services.AddTransient<X>()` cannot construct them. → Register a factory through the class's own method and keep the method: `services.AddTransient(sp => X.Create(sp.GetRequiredService<IUnitOfWorkFactory<IMyUnitOfWork>>()))`. Remove the static fallback inside the constructor (`unitOfWorkFactory ?? UnitOfWorkSource.GetUnitOfWorkFactory()`) so a missing registration fails loudly instead of using a second data source.

## `ViewModelSource.Create` with anything but `new`
`ViewModelSourceException` "Constructor expression can only be of NewExpression type" at run time → `ViewModelSource.Create(() => ...)` reads the lambda as an expression tree and accepts only a constructor call. `ViewModelSource.Create(() => Make(factory))` or `() => X.Create(...)` compiles but throws. → The lambda body is always `new X(...)`; put any other logic before the call.

## Second container
Services registered twice, singletons duplicated → a new `ServiceCollection` was added next to an existing one or next to a Host. → One container; hand its provider to DevExpress.

## Service locator survives
View models call `App.Services.GetRequiredService<T>()` or take `IServiceProvider` → the container became a global. → Constructor injection; the only code that talks to the provider is the composition root (and a custom markup extension before 26.1).

## Static singleton kept alongside the registration
Two instances of "the same" service → `X.Instance` still used in some places after `X` was registered. → Replace every use, then delete `Instance`.

## Designer
Views show nothing in the designer → at design time `{dxmvvm:Ioc}` returns `null` because nothing configured the provider. Expected; design-time data (`d:DataContext`) is the remedy if the user needs it.

## App does not exit
The process stays alive after the main window closes → a Host was started and never stopped, or a window resolved as a singleton is kept hidden. → Stop and dispose the Host in `OnExit`; windows are transient.

## `Application` or `UserControl` is ambiguous
`CS0104` after adding code or `using` directives → DevExpress packages enable WinForms, and `ImplicitUsings` adds `System.Windows.Forms`, which also has `Application` and `UserControl`. → Write the WPF type out in full: `System.Windows.Application`, `System.Windows.Controls.UserControl`.
